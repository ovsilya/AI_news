Retrieval methods

How the pipeline collects news, papers and job posts from about 100 sources, and why each source is read the way it is. Written for readers new to the topic: each method starts with a plain explanation, and the technical details are one click away.

Key words

Collector
The small program in our pipeline that visits a source on a schedule and brings back what's new.
Web page vs. data
A web page is designed for people to look at. Data is designed for programs to read: fixed labels such as title, date and link. Collectors always prefer data, because pages change their look often.
Feed (RSS / Atom)
A file a site publishes that lists its latest posts with title, date and link. RSS and Atom are two formats for the same thing. Feed readers and our collector check it regularly.
API
A web address made for programs. You ask a question ("ML jobs at NVIDIA") and get data back instead of a page.
JSON
The text format most APIs answer in. It looks like "title": "ML Engineer", "city": "Zurich".
API key
A free code you get by registering, which tells the provider who is making the request. Treated like a password.
Release
A new version of a piece of software, published with notes on what changed.
Sitemap
A list of every page on a website, published so that search engines such as Google can find them.
Diff
The difference between two copies of something. We compare today's copy with the last one and keep only what's new.
Proxy
An indirect source standing in for one we can't read directly, such as a Google News search instead of a missing feed.
Scraping
Having a program read pages meant for people and cut out the pieces it needs. Fragile, and many sites forbid it.
robots.txt
A small file where a site says which of its parts automated programs may and may not visit.
Terms of service
A site's rules of use. Several job boards (LinkedIn, Indeed) forbid any automated reading.
Rate limit
The most requests a site accepts in a given time. Going over it gets you slowed down or blocked.

How a method is chosen

Many sources can be read in more than one way. We go down this list and use the first option that works for that source. Options near the top are the ones the site itself offers to programs, so they are allowed, free, and rarely break. Options further down are used only when nothing above exists.

  1. Official feed. The site publishes a list of its latest posts for programs to read. Easiest, free, and clearly allowed.
    Methods: RSS / Atom feed, Filtered feed, Release feed per repo or package
  2. Official API. The site offers a door for programs that answers with clean data, sometimes after a free sign-up.
    Methods: Public JSON API (no key), Official API with a free key
  3. Files the site already publishes for machines. Lists of pages, plain text files, data files, or the job data a careers page loads into your browser.
    Methods: Sitemap diff, Raw file diff, Dataset snapshot diff, Career-site JSON
  4. Compare copies of a page. No feed and no API: save the page each time and see what changed.
    Methods: Page diff
  5. Proxy (an indirect route). Read something that stands in for the missing feed, such as a saved Google News search or a feed made by volunteers.
    Methods: Search proxy: Google News RSS, Community scraper feed, Repo-commits feed as a proxy
  6. Paid search. A company that collects the data legally on its side sells us search results. Used only where the site forbids programs.
    Methods: Search API (SerpApi Google Jobs), xAI X Search (optional, paid)
  7. Emails sent to you. For job boards that allow no programs at all: they email you the jobs, and we read the emails.
    Methods: Job-alert emails via the Gmail API

The checks behind this order: Is it allowed by the site's rules? Is it free or nearly free? Will it keep working if the site changes its design? Is it fresh enough for a brief twice a day? Does it return clean data rather than a page we'd have to pick apart?

Never done: logging in to a site as you, getting past "are you a robot?" checks (CAPTCHAs), scraping sites that forbid it (LinkedIn, Indeed, jobs.ch, Bayt, Naukrigulf), or clicking links inside job-alert emails, which would count as automated visits to those sites.

Rules every collector follows

However a source is read, the collector behaves like a polite, well-identified visitor:

  • Say who we are. When our program visits a site it introduces itself by name, with a link to this project, much like a delivery driver wearing a uniform. If the site owner has a problem, they can contact us instead of simply blocking us.
    Technically: A User-Agent header naming the bot with a contact URL.
  • Only download what changed. Before downloading, the collector asks: "has anything changed since my last visit?" If not, the site replies with a two-line "nothing new" and we skip the download. This saves time and bandwidth on both sides.
    Technically: Conditional GET with ETag / If-Modified-Since; a 304 Not Modified reply means no download and no parsing.
  • Don't overload anyone. We visit each site gently: one request at a time, with a pause in between. If a site says "too many requests" or has a problem, we wait and try later, waiting longer after each failed try.
    Technically: Per-host concurrency of 1, delays between requests, exponential backoff on HTTP 429 and 5xx. Strict sites get more room: Reddit is visited at most every 30 seconds, and after a 429 we wait a full minute and try once more.
  • Follow the site's own rules. Feeds and APIs are made for programs, so using them is always fine. For anything else, the collector first reads the site's robots.txt and stays out of any part the site asks programs to avoid.
    Technically: robots.txt is checked for everything that isn't an official feed or API.
  • Read the article, not just the headline. Many feeds only send a headline or a one-line teaser, which is too little to explain a story. For the stories that make it into the brief, the collector opens the article page once, checks robots.txt first, and keeps only the main text for the writer to read. It never gets around a paywall: a paywalled page simply gives a teaser. Each story in the brief then says how much the writer had: the full article, a paper abstract, an excerpt, or only the headline, so you know when to open the link yourself.
    Technically: For each chosen story with under 800 characters of text: one GET of the article URL (robots.txt honoured), main text extracted with trafilatura, cached for 30 days. Google News links can't be opened directly and are skipped. Coverage flag: 600+ characters of body text is a full article; under 60 beyond the headline is headline only.
  • Keep only what's on topic. Some search feeds are broad: a search for Reuters articles about AI also returns elections and oil prices. These feeds get a keyword filter, so only headlines about AI (or, for the jobs search, about work and jobs) are kept.
    Technically: Per-source keyword filters on title and summary; acronyms such as AI match whole words only.
  • Notice when a source goes quiet. Sources break silently. After a redesign, a feed can simply come back empty. Each source has an expected rhythm (say, about one post a week). If it errors, returns nothing, or stays silent much longer than usual, it is flagged in the weekly report so it can be fixed or replaced.
    Technically: Source health check: zero items, errors, or no new items beyond the usual cadence raise an alert.
  • Keep keys locked away. API keys work like passwords. They live in Google Secret Manager, a locked vault in our cloud account that the program opens when it runs. They are never written into the code, which is public on GitHub.
    Technically: Secrets come from Secret Manager at run time; never in the repo or the container image.

All methods

RSS / Atom feed

Most blogs and news sites publish a feed: a small file that lists their latest posts (title, date, link) in a standard format. RSS and Atom are two versions of the same idea. Our collector opens that file twice a day and keeps anything it hasn't seen before. It's like subscribing to a magazine instead of walking to the newsstand to check whether a new issue is out. Why we prefer it: the site publishes the feed precisely so that programs can read it, so it is allowed, free, and rarely breaks.

Technical details

How it works: Fetch the publisher's feed with a feed-reader User-Agent and conditional headers (If-None-Match / If-Modified-Since). A 304 reply means nothing changed and costs nothing to parse. New items are recognised by GUID or link and passed to dedup.

Why this method: The feed is the publisher's own machine-readable channel: allowed by design, stable for years, and it gives a clean title, date and link without parsing HTML. One cheap request per source per run.

Watch-outs: Paywalled sites send only a headline and teaser, so the brief links out. A few feeds need a browser-like User-Agent (VentureBeat). Intermittent 404s are retried with backoff. Some feeds re-date old posts when they are edited (the LangChain blog does), so every link a feed lists is remembered, and a new source's first fetch only records what is there.

Used in: Vendors & changelogs, Newsletters, Research, Community, Business & policy, Compute & systems, Job boards

Filtered feed

Some feeds include everything a big organisation announces. AWS, for example, posts dozens of updates a day, most of them unrelated to AI. We read the whole feed but keep only the items whose titles contain words we care about, such as "Bedrock" or "AI". Why: we still catch the important announcements, without paying the AI model to read hundreds of irrelevant ones.

Technical details

How it works: Same as an RSS/Atom feed, then keep only items whose title or category matches a keyword list, for example Bedrock and SageMaker for AWS, Technology and Gulf for Semafor, AI/KI for the Swiss federal news service.

Why this method: Generalist feeds publish dozens of items a day and most are irrelevant. Filtering before the LLM stage keeps scoring cost and noise down, while still covering announcements that appear nowhere else.

Watch-outs: Keyword lists drift. The weekly recall check flags stories we missed, and the list is widened when that happens.

Used in: Vendors & changelogs, Newsletters, Community, Business & policy

Release feed per repo or package

When a software project ships a new version, GitHub (where most code is hosted) and PyPI (the store for Python packages) automatically add it to a release feed for that project. We follow the release feeds of the tools you use, such as vLLM and LangGraph. Why: a new version is often the very first sign that a new model or feature exists, sometimes days before anyone writes about it.

Technical details

How it works: GitHub publishes github.com/{owner}/{repo}/releases.atom for every repository with no authentication; PyPI publishes an RSS feed per package. We poll one feed per tracked repo or package.

Why this method: A release is the earliest reliable sign that a model or feature has landed in the tools you actually use (vLLM often supports a new model before any blog post). The Atom feeds avoid the GitHub REST API limit of 60 unauthenticated requests per hour.

Watch-outs: Release candidates and nightlies are noisy, so tags containing rc, dev or nightly are skipped unless they are major versions.

Used in: Models & code, Compute & systems

Public JSON API (no key)

Some sites have a door built for programs instead of people, called an API. You send a request to a special web address and get back clean, labelled data (title, upvotes, salary, city) instead of a page designed for human eyes. These public APIs need no sign-up. Why: we get exactly the fields we need with no guesswork. Job-board APIs like Greenhouse exist so that companies' jobs reach as many places as possible, so reading them is what they're for.

Technical details

How it works: Call a public endpoint that returns JSON: HN Algolia search, HF Daily Papers and trending, OpenRouter /models, Apple's podcast directory, the Greenhouse, Lever, Ashby and SmartRecruiters job-board APIs, the Bluesky AppView, npm.

Why this method: Fields we rank on (points, upvotes, prices, context length, salary, location) come back typed, with no scraping. Job-board APIs exist precisely so that postings get syndicated, so polling them is the intended use.

Watch-outs: Respect each provider's rate limit and cache responses. A schema change shows up as zero items, which the source health check reports.

Used in: Research, Models & code, Community, Job boards

Official API with a free key

The same kind of door for programs, but you first register for a free key: a code, like a library card, that tells the provider who is asking. It lets them count requests and keep usage fair. Why: it is the provider's official, approved route, and often returns the most complete data (Reed, for example, includes the full job description and salary).

Technical details

How it works: Same as a public JSON API, but with a free registration key kept in Secret Manager: Reed, USAJobs, Adzuna, Semantic Scholar, Artificial Analysis (and Congress.gov later).

Why this method: It is the provider's sanctioned route: the terms allow it, the data is complete (Reed returns full descriptions and salaries) and quotas are documented, so calls can be planned.

Watch-outs: Quotas are tight on some (Artificial Analysis 100 requests a day, Adzuna 2,500 a month). Some require attribution, which goes in the brief's footer.

Used in: Research, Models & code, Job boards

Sitemap diff

Most websites publish a sitemap: a plain list of every page on the site, made for search engines such as Google. If the list contains an address that wasn't there last time, a new page (an article, a job) has been published, and we open only that page. Why: the list is meant to be read by programs, so it is reliable and allowed, and it tells us exactly what is new without reading the whole site.

Technical details

How it works: Read sitemap.xml, which lists every URL on the site (often with a lastmod date), diff the URL set against the previous copy, then fetch only the new pages.

Why this method: Sitemaps are published for crawlers, so they rarely change format and tell us exactly which URLs are new. That is sturdier than parsing a listing page. Used for Anthropic News and SuccessFactors career sites.

Watch-outs: lastmod is sometimes missing or bumped on every page, so we diff the set of URLs, not the dates.

Used in: Vendors & changelogs, Job boards

Raw file diff

Some tools keep their version history in a single text file inside their code repository, called a changelog. We download that plain text file and look for new entries at the top. Why: it is the only place those tools announce changes, and a plain text file is the simplest thing to read reliably.

Technical details

How it works: Fetch the raw file (for example CHANGELOG.md on raw.githubusercontent.com), diff it against the last version, and parse the new version headings.

Why this method: Some tools document releases only in a changelog file (Claude Code). A raw file is plain text, supports ETag caching and needs no HTML parsing.

Watch-outs: Headings must follow a version pattern; if the format changes, the parser falls back to sending the raw diff to the LLM.

Used in: Models & code

Dataset snapshot diff

Some information is published as a data file, like a spreadsheet, rather than as an article. One example is the leaderboard that ranks AI models. We download it every week and compare it with last week's copy to spot changes such as "a new model entered the top 5". Why: the facts come straight from the source data, and the licence allows reuse as long as the source is credited.

Technical details

How it works: Download a published dataset (the Arena leaderboard on Hugging Face, the Indeed Hiring Lab CSV), store it, and diff it against the previous copy.

Why this method: Leaderboards and labour-market indices are published as data, not articles. A diff yields facts with a source, such as 'model X entered the top 5' or 'AI share of postings up 0.4 points', and the CC-BY licences allow reuse with attribution.

Watch-outs: Weekly or monthly cadence only. Column changes are caught by schema validation.

Used in: Models & code, Job boards

Career-site JSON

When you open a big company's careers page (say NVIDIA's, which runs on a system called Workday), your browser quietly asks the site for the list of jobs in a data format. Our collector sends the same request your browser would, slowly and politely. Why: large banks, pharma and tech companies don't use the simpler job-board APIs, and this is the company's own job list, complete with full descriptions and often salaries, not a third-party job board with its own rules.

Technical details

How it works: Large employers' career sites (Workday, Oracle Recruiting) load their job lists from a JSON endpoint in the browser. We call the same endpoint: Workday POST …/wday/cxs/{tenant}/{site}/jobs with a search text, 20 results per page; Oracle hcmRestApi/…/recruitingCEJobRequisitions.

Why this method: Banks, pharma, NVIDIA and many other large employers don't use Greenhouse or Lever, and their roles matter most in CH, UK and CA. The endpoints return full descriptions and salary ranges, robots.txt allows the path, and it is the employer's own site, so no job-board terms are involved.

Watch-outs: Undocumented, so it can change without notice. Per site and day: seven keyword searches (usually 10–70 requests), up to 60 new postings read and up to 30 closure checks, one request a second, with our User-Agent. Only the career sites robots.txt allows are used (RBC's main site is disallowed, so RBC is out). Each site's status is recorded in job_boards.

Used in: Job boards

Page diff

Some important pages have no feed. For example, Claude's API release notes are just a web page that gets longer over time. So we save a copy of the page every time we check and compare it with the previous copy; whatever is new is the news. Think of photographing a noticeboard every morning and circling what has been pinned since yesterday. Why: it is the only option for these pages, and it costs just one page visit per check.

Technical details

How it works: Fetch the page, extract the main content as markdown, and compare it with the previous snapshot kept in GCS. Only the new or changed section is sent to the LLM.

Why this method: Several important sources publish no feed at all: Anthropic Engineering, the Claude and Gemini API release notes, the Meta AI blog, The Batch. A diff turns a static page into a change feed for the price of one request per run.

Watch-outs: Layout changes create false positives, so whitespace is normalised and navigation and footers are dropped. robots.txt is respected and each page is fetched at most twice a day.

Used in: Vendors & changelogs, Newsletters

Search proxy: Google News RSS

Reuters, for example, offers no feed. But Google News lets you save a search ("Reuters articles about AI from the last week") and receive the results as a feed. We use that search feed as a stand-in for the missing one. This is what proxy means here: an indirect route to the same information. Google's links pass through a redirect first, so we follow each one to the original article. Why: it is free, needs no key, and doesn't involve copying the publisher's site.

Technical details

How it works: A saved Google News RSS search, for example site:reuters.com "artificial intelligence" when:7d. Each item links to a news.google.com redirect, which is resolved to the original URL before dedup.

Why this method: For sources without a feed (Reuters) or topics without a single source (UAE AI, US state AI bills), a saved query is the cheapest legal way to get a headline stream: no key and no scraping of the publisher.

Watch-outs: Headlines only. Unresolved redirects would break dedup. Google can change the format, so the health check watches the item count.

Used in: Business & policy

Community scraper feed

For a few sites with no feed, volunteers run an open-source project that checks those sites and publishes a feed for them. We read that ready-made feed instead of building our own scraper. Why: someone else maintains it, at no cost to us. If the volunteers stop, only that one source is affected and we switch to comparing page copies (page diff).

Technical details

How it works: Use an RSS file produced by an open-source project (Olshansk/rss-feeds on GitHub) that scrapes sites lacking feeds and commits the XML to the repo.

Why this method: It provides a feed for blogs that have none (the AISI blog, and Anthropic News as a fallback) without us running a scraper. If it stops, only that one source is affected.

Watch-outs: Third party, so it can go stale. The health check alerts when there has been no new item for a set number of days, and the page diff takes over.

Used in: Vendors & changelogs, Business & policy

Repo-commits feed as a proxy

Some blogs are built from files kept on GitHub. Every new post means someone saved ("committed") a new file, and GitHub publishes a feed of those saves. So a new save that adds a post tells us a new article is out. Why: the blog has no feed of its own, but this one appears automatically and is free.

Technical details

How it works: Some blogs are static sites built from a GitHub repo (LMSYS / SGLang). The repo's commits/main.atom lists every commit, and we keep commits that add a post.

Why this method: There is no RSS, but a new post always means a commit. Free, no authentication.

Watch-outs: Noisy (typo fixes, styling), so commits are filtered by message and by files added under the posts directory.

Used in: Compute & systems

Search API (SerpApi Google Jobs)

LinkedIn and Indeed forbid programs from reading their sites. Google Jobs gathers job posts from across the web, and a company called SerpApi runs Google Jobs searches for its customers and returns the results as clean data. Why: we see jobs from everywhere without breaking anyone's rules ourselves. The free plan allows 250 searches a month, so we search twice a week.

Technical details

How it works: SerpApi runs Google Jobs searches for us (gl = us, ca, uk, ch, ae plus a location) and returns JSON, including apply_options links that point to the employer's own job page.

Why this method: Google Jobs aggregates postings from boards we must not scrape (LinkedIn, Indeed, Bayt). SerpApi carries the scraping and legal risk, and we receive structured results. It is the main programmatic source for the UAE.

Watch-outs: The free tier is 250 searches a month, hence the twice-weekly schedule. Descriptions may be truncated, so postings are enriched from the employer link.

Used in: Job boards

xAI X Search (optional, paid)

X (formerly Twitter) charges a lot for official access to its data and forbids scraping. xAI, the company behind the Grok model, sells a cheap search over X posts. We could use it to follow about 50 researchers. Why optional: the AINews newsletter already summarises the important X discussions, so this is only worth paying for later.

Technical details

How it works: Use xAI's API search tool to query recent posts from about 50 chosen researcher and lab accounts.

Why this method: The official X API costs $200+ a month and scraping X breaks its terms; xAI's search tool is the cheapest sanctioned route at about $5–10 a month. It is optional because AINews already recaps X.

Watch-outs: Paid per call, so it is capped by the budget alert.

Used in: Community

Job-alert emails via the Gmail API

You sign up for job alerts on LinkedIn, Indeed and other boards, just as any job seeker would. The alerts arrive in your Gmail, and the pipeline reads them with read-only permission: it can read those emails but cannot send, change or delete anything. Why: the sites emailed you those jobs themselves, so this is fully within their rules. We never click the links in the emails; instead we look up each job on the company's own site.

Technical details

How it works: You subscribe to alerts (LinkedIn, Indeed, jobs.ch, Bayt and others). A Gmail filter labels them; the pipeline reads that label with the gmail.readonly scope, parses each sender's template, strips tracking parameters and dedups.

Why this method: It is the only terms-safe way to see what those boards show you, because they send it to you on purpose. The scope is read-only, and the pipeline never opens board links (that would be automated access); it looks for the employer's own posting instead.

Watch-outs: The OAuth app must be set to 'In production', otherwise refresh tokens expire after 7 days. Template changes break parsers, so each sender has parser tests. Recruiter personal data is stripped.

Used in: Job boards

LLM extraction from free text

Some job posts are just a paragraph a person typed, such as the comments in Hacker News' monthly "Who is hiring?" thread. A cheap AI model (Gemini Flash-Lite) reads each one and fills in a fixed form: company, title, city, remote or not, salary, skills. Why: it turns messy text into data we can count and compare, for a few cents a month.

Technical details

How it works: Text retrieved by another method (for example HN 'Who is hiring' comments via the Algolia API) is turned into a strict JSON record by Gemini 3.1 Flash-Lite: company, title, location, remote, salary, skills.

Why this method: Some valuable data has no structure at all. At $0.25 per million input tokens, parsing a few hundred comments a month costs cents, and the strict schema rejects invented fields.

Watch-outs: Every record is validated against the schema and keeps a link to the source comment.

Used in: Job boards

Links counted as votes

Newsletters such as TLDR AI already pick out the day's important stories. Instead of copying their summaries, we note which articles they link to. Every newsletter that links to a story counts as one vote that the story matters. Why: it borrows the judgement of human editors, and because we always go to the original article, the same story isn't counted twice.

Technical details

How it works: Outbound links in a newsletter are extracted, resolved to their canonical URL, and each adds a vote to the matching story cluster.

Why this method: Newsletter editors have already filtered the day, so their picks are a strong importance signal. Counting links (rather than ingesting the newsletter's own summary) also stops a newsletter copy from becoming a duplicate story.

Watch-outs: Sponsored links are dropped by a domain and keyword list.

Used in: Newsletters
