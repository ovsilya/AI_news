AI_news: architecture

A daily AI-industry brief that runs on GCP and posts to Telegram, plus job-market tracking and a career-fit report. Markets: USA · Canada · UK · Switzerland · UAE. Draft v1.0 · 2026-10-13. Status: Phase 1 runs on the laptop: it collects the sources, judges and writes the brief through Vertex AI on the personal GCP project, and posts to Telegram when asked (ainews run, then ainews send; ainews tg-clean clears earlier test posts). The jobs lane runs by hand too: ainews jobs polls 97 employer job boards and 32 Workday career sites and reads new postings, ainews weekly builds the jobs report; How the job search works explains it step by step. Cloud Run, Cloud Scheduler, Cloud Storage and Firestore below are the deployment plan. Hover a block for a quick tooltip, or click it to see what it does and why.

How the three lanes relate

The lanes are three separate runs of the same container, each on its own schedule. They never call each other: they only read and write the SQLite database. Inside a lane the steps run in order.

  1. ② Jobs (05:00) polls the job boards, extracts new postings and updates the skill statistics.
  2. ① Brief (06:00) will read those results for a career section in the brief (planned; today the brief doesn't use them). The 18:00 run is a lighter update that only covers what changed since morning.
  3. ③ Weekly (Mon 07:00) reads the ② postings to compute skill shares, trends and your market fit, then writes the jobs report. A State of the field report from the week's ① stories comes later.

Because the job runs with parallelism 1, only one run at a time can write the database. A run that finds the snapshot locked waits, or fails and retries.

How the job search works

Lanes ② and ③ have their own guide, with diagrams, real numbers from the first runs, and two small tools to try. Start with the overview, or go straight to a step:

  1. Sources: 97 employers whose job-board APIs return the full list, and 32 Workday career sites searched for AI roles. Which employers, and how a new one is found.
  2. Filter & track (J1): title rules pick your target roles and location rules your markets; comparing with what's stored finds new, changed and closed postings. With a title tester.
  3. Read (J2): Gemini 3.1 Flash-Lite fills in the same form for every new posting: role, seniority, skills, pay. With a worked example.
  4. Count, explain, publish (J3, W1–W3): skill shares, rising and falling skills, your fit, three short notes, and the channel post. With an “is this skill rising?” tool.
  5. Run & change it: commands, settings, adding an employer, the tables, and what to do when something looks wrong.

How profile edits work (option B)

  1. You send a plain-text message, voice note, GitHub repo link or PDF in the private chat with the bot. For example: “Shipped an MCP server with FastMCP on Cloud Run”.
  2. The webhook replies “⏳ parsing…” straight away and queues the work in Cloud Tasks.
  3. The input is normalised: voice is transcribed; repo READMEs and dependency files, or PDF text, are fetched and treated as data, never as instructions.
  4. Gemini Flash-Lite receives your current profile JSON and the input, and returns a strict-schema list of add / update / remove changes, each with a reason and evidence. If anything is ambiguous, the bot asks one clarifying question instead of guessing.
  5. The bot shows the diff with three buttons: ✅ Apply · ✏️ Edit · ❌ Cancel.
  6. Apply writes a new profile version in a Firestore transaction. /undo goes back one version and /history lists them. The next pipeline run uses the new version.

The weekly run can also suggest changes, for example “you 👍’d six MCP stories; add MCP = portfolio?”. These come to the same private chat for your approval.

Orchestration

Cloud Scheduler

What: Three cron triggers, which is the free quota: ① the brief at 06:00 and 18:00, ② jobs at 05:00, ③ the weekly reports Mondays at 07:00.

Why: Managed cron with no server to run. Jobs finish before the morning brief, so the brief can include fresh postings.

↑ back to diagram

Cloud Run Job

What: One container image with three modes (run daily | jobs | weekly), 1 vCPU / 2 GiB, parallelism 1.

Why: Pay-per-run, so it fits the free tier. Running a single writer means the SQLite snapshot is never written by two runs at once.

① Daily brief

1 · Ingest

What: Fetches every source politely: conditional GET so unchanged feeds aren't re-downloaded, a pause between requests to the same site (30 s for Reddit, which rate-limits hard) and a one-minute wait after a 429. RSS items keep the full post when the feed carries it (up to 4,000 characters). Broad search feeds keep only on-topic headlines: AI for Reuters, work and jobs for the AI-and-jobs search. Records the health of each source.

Why: Incremental, polite fetching keeps runs cheap and avoids being blocked. Full feed text gives the editor real facts to explain. The health check catches feeds that move or die.

↑ back to diagram

2 · Dedup

What: Three passes: canonical URL, then MinHash near-duplicate text, then embedding similarity against the last 72 hours (the embedding pass comes in Phase 2; until then the editor merges stories that are about the same event).

Why: The same launch arrives 5–10 times. Each pass is cheap enough to run before the next, so the LLM never sees a duplicate.

↑ back to diagram

3 · Cluster & heat

What: Adds each item to an existing story or starts a new one. Heat counts the distinct sources covering a story, weighted by their authority, and decays over 24 hours.

Why: Stable story IDs let follow-ups attach to yesterday's story. Heat measures importance regardless of your profile.

↑ back to diagram

4 · Score (Flash-Lite)

What: Builds a batch of up to 120 candidates: first the best story from every source, then a fair share per layer, then the hottest of the rest. Flash-Lite scores each against your profile for relevance, novelty, actionability and credibility, and assigns a section: big picture, trends & future of work, models, tools, research, systems or community. Trend and big-picture stories are ranked without actionability. The final pick allows one story per source (three for the multi-outlet jobs search).

Why: A cheap model for bulk judgement. Giving every source a slot stops busy outlets from crowding out small ones, and the per-section and per-source limits keep the brief broad and varied, not limited to your own role or one vendor's blog.

↑ back to diagram

5 · Write brief (3.5 Flash-Lite)

What: Stories that arrived with only a headline or teaser first get the main text of their article page (robots.txt honoured, extracted with trafilatura). Gemini 3.5 Flash-Lite then writes at most 15 items in a teaching style: What happened (4–7 sentences); What is it? (an intro plus labelled points such as How it works, Analogy, Why now, Connects to); and Comment from a pro (a senior engineer guiding your career: Learn, Try, At work, Career, Interview). A career section from ② data is planned.

Why: You're learning these topics, so every story explains the idea and what it means for your work and career. Article text gives the editor facts to explain instead of a headline. A slightly stronger model than the judge writes noticeably better explanations, for 2–3 cents a brief.

↑ back to diagram

6 · Verify & publish

What: Drops items that cite unknown or repeated stories, removes every sentence or bullet whose numbers aren't in the sources (0.30 and 0.3 count as the same number), and keeps at most 15 items. Then posts the brief in as few messages as possible: a contents list first, then whole stories packed up to Telegram's limit, each with its date and a flag for how much the editor read (full article, abstract, excerpt or headline only). Only the first message notifies. Stores the message IDs. Sentence-level citations and feedback buttons come in Phase 2.

Why: Summaries have to be trustworthy: the model can't slip in a number the sources don't support. Each message on a phone is a notification, so stories are packed into few messages; the flag says when a summary rests on a headline only, so you know to open the link. The stored message IDs will connect each button click to its story.

② Jobs

J1 · Poll & diff

What: Fetches the full list of open postings from 97 employers' own job boards through the public Greenhouse, Lever and Ashby APIs (about 13,000 postings in 80 seconds), and searches the Workday career sites of 32 banks, pharma and big-tech employers for AI roles within our countries. Keeps the ones in your target role families (FDE and applied AI, solutions, LLM/GenAI, AI and ML engineering; ML research and data science for context) and markets (US, CA, UK, CH, UAE, remote), about 2,400. Compares with what is stored: new, changed and closed (missing for 36 hours from successful polls; on Workday, only once the posting's own page says it is gone). SerpApi Google Jobs and alert emails come next.

Why: Only new or changed postings need model work. Closing dates will show how long roles stay open. A full list per employer makes the diff exact, which is why the boards with complete public lists came first.

J2 · Extract (Flash-Lite)

What: Gemini 3.1 Flash-Lite reads five postings per call into strict JSON: role family (judged from the duties, not the title), seniority, years asked for, required and preferred skills, customer-facing work, travel, remote policy, visa sponsorship, salary and a one-line summary. Skills are mapped to about 150 canonical names (config/skills.yaml); a salary the board publishes wins over one read from the text. About $0.001 a posting, at most 200 per run.

Why: Converts free text into comparable fields, cheaply. A posting is read again only when its text or the prompt changes.

J3 · Aggregate

What: Computes, in code, skill shares across open postings in your target roles (overall and by role family); counts by market, seniority, remote and customer-facing work; median posted pay ranges; and who is hiring most. Rising and falling skills compare postings published this week with the four weeks before, only when the Wilson 95% intervals don't overlap, and only after two weeks of tracking. Flagging matching postings for the daily brief comes next.

Why: The numbers come from the data, not the model, so the report can be trusted. Waiting two weeks for trends avoids inventing them: during the first backfill the earlier period holds only postings that were still open.

③ Weekly

W1 · Trends & fit

What: Takes J3's statistics and your private skills list (private/skills.yaml: have and learning) and computes coverage: the demand-weighted share of the top 30 skills you have. Lists the biggest gaps, marking the ones you are already learning and the ones that are rising. Topic bursts in the news come later.

Why: Answers 'am I keeping up?' with data rather than a feeling.

Storage & platform

Cloud Storage

What: Holds the SQLite database snapshot: downloaded at the start of a run and uploaded at the end, but only if no other run has changed it in between. Also holds the brief archive and weekly profile exports.

Why: SQLite is the simplest database for a single writer, and GCS keeps it durable for free. Writing SQLite directly over GCS FUSE is unsafe because FUSE has no file locking.

↑ back to diagram

Firestore

What: Stores feedback clicks, your versioned profile (skills, projects, portfolio, targets), and bot state such as edits waiting for approval.

Why: The bot is stateless and can run several copies at once, and Firestore handles small simultaneous writes on the free tier. Every run merges this data into SQLite.

↑ back to diagram

tg-bot (Cloud Run service)

What: Receives Telegram updates by webhook: button clicks, commands and profile edits. It acknowledges straight away and hands slow work to Cloud Tasks: transcribing voice notes, fetching repos and PDFs, and the Flash-Lite call that drafts a profile change.

Why: Scales to zero, so it costs about $0, yet buttons respond instantly. Polling Telegram instead would need an always-on instance at about $12/mo.

↑ back to diagram

Platform services

What: Secret Manager for the bot token, Artifact Registry for the image, Cloud Tasks for async bot work, Logging, and a monthly budget of CAD 14 (about US$10; the billing account is in CAD) with email alerts at 25, 50, 90 and 100% of spend and at 100% of the forecast.

Why: Keeps secrets out of the public repo and needs no servers. Billing data lags by hours, so the budget is a backstop and the app's spending guard (see Vertex AI) is the real-time limit. There is no billing kill switch, because the project is shared with other work and unlinking billing would stop all of it.

↑ back to diagram

Vertex AI

What: Gemini 3.1 Flash-Lite for scoring, extraction and parsing bot edits; Gemini 3.5 Flash-Lite for writing the teaching-style brief (3.8 Flash if more quality is needed); gemini-embedding-2; speech for voice notes and an optional audio brief. Every call goes through the app's spending guard: an on/off switch (AINEWS_LLM_ENABLED) and caps of $0.30 per run, $0.75 per day and $10 per month, checked against the call's worst-case cost before it is sent. Responses that are cut off or blocked are still logged with their cost.

Why: One billing account and IAM authentication, with no API keys. Google's own models need no access request, and the global endpoint is about 10% cheaper than regional ones. Gemini runs on shared capacity with no per-project quota to lower, so the app's caps are the real-time protection. Expected cost: about $2–3 a month. Claude stays available as an optional provider.

Delivery & control

Telegram channel

What: Carries the brief in as few messages as possible (14 stories fit in about 8): a contents list, then each story with its section, title, date and coverage flag, what happened, the two teaching notes as quoted blocks with bullet points, and the source links. The evening edition covers only what changed since the morning. Weekly reports come with lane ③, and 👍 👎 🔇 buttons with the bot webhook (Phase 2): one row per story under the message that holds it.

Why: Telegram is the delivery channel you chose. Few messages means few phone notifications; buttons can later rate each story, one row per story. ainews tg-clean removes test posts, keeping the latest brief.
