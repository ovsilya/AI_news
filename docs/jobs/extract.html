3 · Read each posting with the model

A title and a location don't say what a job asks for. So Gemini 3.1 Flash-Lite reads each new or changed posting and fills in the same form: role family, seniority, skills, remote policy, pay and more. Code then tidies the answers so they can be counted, for example so that “k8s” and “Kubernetes” are the same skill. This is step J2 on the architecture diagram.

Why a model, and why this one

Postings are long, inconsistent prose. One says “must have 5+ years of Python”, another “you're fluent in Python”. Rules can't reliably pull skills, seniority and pay out of that; a model reads it the way a person would. The cheapest Gemini model is enough, because it fills in a fixed form instead of writing anything creative, and the form is checked by a strict JSON schema: every answer must have exactly these fields, with values from fixed lists. Five postings per call keeps the instructions (and the 147 skill names) from being sent once per posting.

The form the model fills in

The prompt is prompts/job_extract.md (version jobs-extract-v1). Its main rules:

  • Judge the role family from the duties, not just the title, and file roles where AI is only the company's product as “other”.
  • Split skills into required and preferred by the posting's own words (“must” versus “nice to have”); if it doesn't say, they count as required. At most 15 required and 10 preferred, most important first.
  • Use the canonical skill names whenever one fits; otherwise a short common name (“Kubernetes”, not “experience running k8s clusters”). Skip generic traits such as “passion”; keep concrete ones such as “Customer-facing work”.
  • Use only what the posting says. No skills guessed from the company's reputation, and a salary only if the text states one.

A worked example

Legora's “Junior/Mid-level Forward Deployed Engineer” in New York City: 6,246 characters of posting text, and a salary range the board publishes as a structured field ($175,100–$245,000 a year). The model's form, after code tidied it:

{
  "role_family": "fde_applied_ai",
  "seniority": "mid",
  "years_min": 2,
  "skills_required": ["Software engineering", "REST APIs", "Authentication", "Integration",
                      "Data pipelines", "Customer-facing work", "Communication", "Debugging"],
  "skills_preferred": ["TypeScript", "B2B", "AI agents", "Product sense"],
  "customer_facing": true,
  "travel": "unknown",
  "remote_policy": "onsite",
  "visa_sponsorship": "unknown",
  "summary": "Builds and deploys integrations and software solutions by working directly with
              enterprise customers to solve their specific legal workflow needs.",
  "salary": {"min": 175100, "max": 245000, "currency": "USD", "period": "year", "source": "board"}
}
  • Seniority “mid” and 2 years: taken from the title and the years the posting asks for.
  • Skills: names such as “REST APIs”, “Customer-facing work” and “AI agents” are canonical names from the dictionary below. “B2B” and “Authentication” aren't in it, so they are kept as the model wrote them.
  • Salary, source “board”: the board's own number was used, not the model's reading of the text.
  • Travel and visa “unknown”: the posting doesn't say, and the model is told not to guess.

When the title misleads. Cloudflare's “Senior Forward Deployed Infrastructure Engineer” looks like an FDE role by its title. The model read the duties (“collaborates with strategic customers to deploy and manage large-scale infrastructure and compute capacity”) and filed it as Solutions engineer. The report uses the model's family, so infrastructure roles don't inflate the FDE numbers.

The skills dictionary

Counting skills only works if each skill has one name. config/skills.yaml holds 147 canonical names in 12 categories, each with its aliases. The model is given the names; code then maps whatever it wrote through the aliases, ignoring case: “k8s” becomes Kubernetes and “sklearn” becomes scikit-learn. A skill that appears in both lists counts once, as required.

The weekly statistics apply today's dictionary to every stored form. Adding an alias therefore also fixes postings read weeks ago, with no need to read them again.

Pay: whose number wins

  1. The board's structured salary, when there is one: Greenhouse pay ranges, Lever's salary range or Ashby's compensation. Saved with "source": "board".
  2. Otherwise, a range the model found in the text, which is common in the US because of pay-transparency laws. Saved with "source": "text". It needs a minimum, a maximum and a currency.
  3. Otherwise none. Bonuses, equity and “competitive salary” don't count.

Of the first 210 postings read, 105 had a board salary, 17 a salary in the text, and 88 none. Workday boards have no salary field, so their pay always comes from the text.

When a posting is read again

  • Its text changed: the stored fingerprint (hash) of the title and text no longer matches the form's.
  • The prompt changed: raising the version at the top of prompts/job_extract.md makes every open posting due again, newest first.
  • Never for closed postings: only open postings are read.

Cost, speed and limits

Per postingAbout $0.0011: roughly 1,600 tokens in and 460 out (the first 210 postings cost $0.23 in 42 calls)
Per runUp to 200 postings (AINEWS_MAX_JOBS_EXTRACT), newest first: about $0.22 and 4 minutes for 40 calls
Spending guardEvery call is checked against the caps first ($0.30 a run, $0.75 a day, $10 a month). A call that could break a cap isn't sent; reading stops cleanly and resumes on the next run
A failed batchLogged and skipped; its five postings stay unread and are tried again next run
The backlogOn 13 Oct 2026, 2,065 postings were waiting: about ten daily runs, or five if you run it twice a day
