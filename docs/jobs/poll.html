2 · Filter and track postings

Each day, ainews jobs fetches every employer's postings and keeps the ones that fit you. That means a title in one of your role families and a location in one of your markets. It then compares them with what is stored, to find postings that are new, changed or closed. This is step J1 on the architecture diagram, and it uses no model.

Filter 1: the title decides the role family

Titles are checked in three passes:

  1. Is it an engineering or science role at all? The title must contain one of: engineer, engineering, architect, developer, scientist, deployed, deployment, strategist, researcher, technical staff. “Product Manager, AI” is not kept.
  2. Is it a role we never track? Intern, internship, recruiter, account executive or manager, counsel, attorney, paralegal, designer, writer, sales or business development, talent.
  3. Which family? The rules below are tried in order, and the first match wins. So “Applied AI Solutions Architect” is FDE / applied AI rather than Solutions engineer, and “LLM Inference Engineer” is LLM / GenAI rather than ML engineer.

Your 5 target families are FDE / applied AI, Solutions engineer, LLM / GenAI engineer, AI engineer, ML engineer. ML research and data science are kept too, for context, and appear in the report as “Also open”.

The title gives only a first guess. When the model reads the posting (step 3) it judges the family again from the duties, and the report uses the model's judgement. For example, Cloudflare's “Senior Forward Deployed Infrastructure Engineer” deploys and runs infrastructure for strategic customers, so the model files it as a solutions role.

Filter 2: the location decides the market

Your markets are the USA, Canada, UK, Switzerland, UAE, plus remote. A posting is kept if any of its locations is in one of them. Locations are free text, so they're matched in four ways:

  • Country and city names, in any case: “United States”, “Canada”, “London”, “Zürich”, “Dubai”, “Bay Area”, about 70 names in all.
  • US state and Canadian province codes after a comma, in capitals only: “Austin, TX”, “Toronto, ON”. Capitals only, because “New York, On-site” must not count as Ontario.
  • The board's own country field, when it has one: Lever's country, Ashby's address and Workday's country. This catches cities not on the list, such as Barclays' Whippany or Wilmington.
  • Remote: a remote job that names one of your countries counts in both (“Remote - US” is USA and remote). One that names no place counts as remote. One that names another country (“Remote - Germany”) is dropped.

Compare with what's stored: new, changed, closed

Every kept posting gets a key: employer plus the board's own job ID (salesforce:JR123456). Each poll compares the kept postings with the stored ones:

  • New: a key that isn't stored yet. It's saved with “first seen” and “last seen” set to now.
  • Changed: the title or text differs from the stored copy (a fingerprint of the text, its hash, changed). The stored copy is updated, and the model reads it again in step 3.
  • Missing: stored and open, but not in today's poll. It isn't closed straight away: a board can drop a posting for a few hours, or a poll can go wrong.
  • Closed: missing for more than 36 hours, counted only from polls that worked. Its closing time is when it was last seen, so the report can later measure how long roles stay open.
  • A board that fails closes nothing. If an employer's board errors (timeout, server error), the error is recorded in job_boards and the board is skipped for the day. Its postings keep their old “last seen”.

Workday: searching instead of listing

Workday has no full list, and search results are ranked by relevance, so their order shifts from day to day. A posting missing from today's results may still be open. So each Workday site goes through these steps:

  1. Check robots.txt. The site must be one that its robots.txt allows. If not, the board is recorded as an error and nothing is fetched.
  2. Find the country filter. One request reads the site's filters, and the country filter gets ticked for the US, Canada, UK, Switzerland and UAE. Tenants name it differently (locationCountry, Location_Country, NVIDIA's locationHierarchy1), so a filter counts if its name says “country” or at least a tenth of its values are your countries. That rule rejects city lists that happen to contain “United Kingdom” (Roche, AstraZeneca). Without a country filter (PayPal, Barclays, Capital One…), the search runs worldwide and the location filter after reading does the job.
  3. Search 7 keywords: “machine learning” · “LLM” · “generative AI” · “AI engineer” · “artificial intelligence” · “forward deployed” · “applied AI”. Each keyword is paged 20 results at a time. Paging stops at a page with no title in a role family, a short page, the end of the results, or 10 pages.
  4. Sort each result by its requisition ID (the employer's own job number):
    • already stored → marked as seen today, with no extra request;
    • read before and outside your roles or markets → ignored (the run remembers these, so they aren't read again);
    • new → read in step 5.
  5. Read each new posting once. One request fetches its own page: the full text, all its places, its country, its start date and whether it's remote. That's up to 60 per site per run; the rest wait for the next run. The title and location filters run again. A kept posting is saved as new; one that isn't is remembered as skipped. A posting that no longer takes applications counts as gone.
  6. Check the missing ones. A stored posting not seen for 36 hours has its own page opened, oldest first, up to 30 per site per run:
    • gone (page not found, no longer posted, applications closed) → closed;
    • still there → kept open (it only dropped down the search ranking);
    • an error → no decision; it's checked again next run.
  7. Save. The searching and reading for 4 sites run at the same time; saving happens one site at a time, in one place.

On 13 Oct 2026: the first Workday run took 6 minutes and found 885 AI-titled results. It saved 503, and 281 waited for the next run. The second run took 4 minutes: 536 results were already stored and needed no request, and 148 were new. The daily run settles at about 4 minutes, mostly spent searching.
